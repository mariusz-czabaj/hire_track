## Vision & Problem Statement

Hiring managers in technical organizations lose time and accuracy chasing reviewer scores after every interview round. Today's workflow is emails and Slack threads — unstructured, unsearchable, and easily forgotten. The same candidate can return months later with no one able to recall what happened in the previous round. The manager enters the decision meeting on gut rather than documented evidence.

The insight: existing ATS tools are built for HR departments and recruiters, not for the technical hiring leader who runs the actual evaluation. A lightweight tool purpose-built for that leader's workflow — candidate profiles, structured reviewer evaluations, historical candidate tracking, and optionally a candidate-facing assignment layer — fills the gap the ATS leaves.

## User & Persona

**Primary: Hiring Manager / Team Lead**
A technical leader responsible for building their team. They coordinate 3–10 interviews per hire cycle, manage a rotating panel of peer reviewers, and own the final hire decision. They reach for this product the day after a round of interviews, when they need to consolidate reviewer notes before the decision meeting. They feel the pain most acutely when the same candidate applies again and there is no record of what was evaluated before.

## Access Control

Multi-user web application with two roles:

- **Admin / HR**: full visibility — all candidate profiles across all competence areas, all reviews. Manages the team.
- **Competence leader** (e.g., DEV lead, QA lead, BA lead): sees only candidates scoped to their competence area. Adds evaluations for those candidates.

Any authenticated user can create a new candidate profile and assign it to a competence area.

One candidate → one competence area → one competence lead. No multi-area assignment in MVP.

Auth: email + password sign-in. Candidate-facing login is out of scope for this MVP.

## Success Criteria

### Primary
A hiring manager can see all candidates, their current pipeline stage, and all competence evaluations in one screen — without sending a single email or Slack message to collect reviewer notes.

### Secondary
A candidate who re-applies is immediately linked to their prior evaluation history, so the hiring manager can see what happened before without digging through email archives.

### Guardrails
- **Competence isolation**: a competence leader scoped to DEV must never see QA-area or BA-area candidate profiles or evaluations. Data leakage between competence areas invalidates trust in the tool.
- **MVP timeline**: 3 weeks after-hours; scope must not expand beyond the pipeline tracking core.

## Functional Requirements

### Authentication & User Management
- FR-001: User can sign in with email and password. Priority: must-have
  > Socrates: Counter-argument considered: password friction may suppress reviewer adoption. Resolution: kept; individual accounts are required for review attribution (FR-012) and competence isolation (FR-007).
- FR-002: Admin can create new user accounts in-app and assign each user a role (Admin or Competence leader) and a competence area. Priority: must-have
  > Socrates: Counter-argument considered: in-app user management is complex to build safely within a 3-week MVP; DB seed may be faster. Resolution: kept; the team cannot touch a database every time someone joins — in-app management is necessary from day one.

### Candidate Management
- FR-003: Any authenticated user can create a candidate profile (name, position applied for, contact info) with a competence area assigned at creation time. Priority: must-have
  > Socrates: Counter-argument considered: open creation risks orphaned or mis-assigned profiles. Resolution: kept; the required competence area field at creation time is the gate. Mis-assignment is an operational issue, not a product blocker.
- FR-004: Any authenticated user can upload a CV / résumé document to a candidate profile. Priority: must-have
  > Socrates: Counter-argument considered: file upload requires storage infrastructure that could cost 1 week in a 3-week MVP; a link field achieves 80% of value with near-zero setup. Resolution: kept; external links are not reliable enough for a hiring record that may be referenced months later.
- FR-005: Admin can view all candidate profiles across all competence areas. Priority: must-have
  > Socrates: Counter-argument considered: unfiltered Admin view becomes unnavigable at 30+ candidates. Resolution: kept as written; grouping/filtering is a UX detail handled in implementation, not an FR constraint.
- FR-006: Competence leader can view candidate profiles in their assigned competence area only. Priority: must-have
  > Socrates: Considered with FR-007 (see below).
- FR-007: System prevents any user from viewing a candidate that belongs to a competence area they are not authorized for. Priority: must-have
  > Socrates: Counter-argument considered: one-area-per-leader rule is a hard constraint that may break if a leader covers two areas later. Resolution: kept; the one-candidate = one-area = one-leader rule is intentional for MVP. Multi-area assignment is a v2 decision.

### Pipeline Stages
- FR-008: Admin can move any candidate through pipeline stages (applied → interviewing → rejected | hired). Priority: must-have
  > Socrates: Considered with FR-009 (see below).
- FR-009: Competence leader can move candidates within their competence area through pipeline stages. Priority: must-have
  > Socrates: Counter-argument considered: stage transitions should require an evaluation before advancing past 'interviewing'. Resolution: kept as free movement for MVP; gate constraints are a v2 feature.

### Evaluations
- FR-010: Competence leader can add a structured evaluation for a candidate in their area (numeric score per skill dimension + free-text summary notes). Priority: must-have
  > Socrates: Counter-argument considered: (a) who defines skill dimensions — hardcoded rubric may not fit all competence areas; (b) visible scores may anchor subsequent reviewers, undermining independent evaluation. Resolution: kept as written; dimension configuration and blind-review ordering are v2 features.
- FR-011: Admin can read all evaluations for any candidate. Priority: must-have
  > Socrates: Considered with FR-012 (see below).
- FR-012: Evaluation is attributed to the named reviewer who submitted it (no anonymous reviews). Priority: must-have
  > Socrates: Counter-argument considered: named attribution may cause reviewers to soften feedback knowing the Admin will see their name. Resolution: kept; accountability is an explicit design goal. Anonymous reviews are a separate product philosophy.

### Historical Tracking
- FR-013: System links a candidate who re-applies to their prior application history, surfacing previous evaluations automatically on the candidate profile. Priority: nice-to-have
  > Socrates: Counter-argument considered: (a) name-based matching is fragile — typos and name changes create ghost duplicates; (b) prior evaluations may pre-bias reviewers against candidates who've grown. Resolution: kept; the matching strategy (email-based preferred) and display framing ("prior history — context only") are implementation concerns. The value of historical context outweighs the risks for MVP.

## Non-Goals

- **No candidate-facing features**: candidates cannot log in, submit assignments, or view their pipeline status in MVP. The app is a tool for the hiring team only.
- **No external HR system integrations**: no sync, import, or export to Workday, BambooHR, LinkedIn, Greenhouse, or similar. Standalone deployment only.
- **No email notifications or workflow automation**: the app does not send alerts when a stage changes or a review is due. Users check the app proactively.
- **No mobile app or offline support**: desktop browser only. No native mobile app, no service worker, no offline mode in MVP.

## Business Logic

The system routes a candidate to their competence domain based on a single selection made at profile creation, gates evaluation access to leaders of that domain only, and consolidates their structured scores into a decision-ready view for the hiring manager.

The sole user-facing input that drives routing is the competence area selected when the candidate profile is created. From that moment, the system derives all downstream access: which leaders can see the candidate, who can move them through pipeline stages, and who can add evaluations. The creator does not need to re-state the routing — the selection at creation is the binding assignment.

The output is a consolidated candidate profile visible to the Admin: pipeline stage, all submitted evaluations with reviewer attribution, scores per dimension, and free-text notes — assembled from multiple competence leaders without any manual aggregation by the hiring manager.

## Non-Functional Requirements

- The product is a browser-based web application, usable on the latest two major versions of mainstream desktop browsers (Chrome, Firefox, Safari, Edge). No mobile or offline requirements in MVP.
- Competence isolation is enforced at the data layer — a competence leader who circumvents the frontend must not receive candidate data outside their authorized area.
- Uploaded CV and résumé files are not served via public URLs. Access to a file requires an authenticated and authorized session; unauthenticated or out-of-scope requests must be rejected.
- The candidate list and individual profile screens load fast enough that a hiring manager does not notice latency during a live decision meeting.

## User Stories

### US-01: Hiring manager reviews consolidated candidate evaluations

- **Given** a logged-in Admin, a candidate profile exists with a competence area assigned, and at least one competence leader has submitted a structured evaluation
- **When** the Admin opens the candidate profile
- **Then** they see the candidate's current pipeline stage and all submitted evaluations (with scores, notes, and reviewer name) in one screen — without contacting any reviewer separately

#### Acceptance Criteria
- All evaluations for the candidate are visible on a single profile view
- Each evaluation shows: reviewer name, date submitted, score per dimension, free-text notes
- Pipeline stage is visible alongside evaluations
